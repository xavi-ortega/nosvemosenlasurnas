# Loop engineer execution contract

This guide turns the canonical plan into bounded autonomous work. It does not start an unattended scheduler. Follow the user's run instruction and stop rules; do not create recurring automation without an explicit scheduling request.

## Before the first iteration

1. Read AGENTS.md, outputs/electoral-app-development-plan.json, outputs/project-language-policy.html and section 17 of the HTML plan. Read applicable Boost skills before their work.
2. Inspect Git and preserve user changes. Read work/execution-journal.jsonl. Verify generated plan consistency with `python3 outputs/render-development-plan.py --check`.
3. Read outputs/approval-gate-01.html. The latest direct user instruction authorizes initial local Laravel/Boost, project skills, baseline CI, Markdown plans, agent guidance and OSS metadata only; see outputs/initial-scaffold-authorization.json. GATE-00 retains that exact scope. Product features still require explicit GATE-01 approval for the displayed design fingerprint. Silence is not approval.
4. Record actual named human owners when provided. A role label is not an assignment; software can implement review permissions before a complete programme inventory exists.

## One iteration

Select the smallest eligible atomic item. All unconditional dependencies must be complete with evidence. Evaluate conditional dependencies for the precise enabled capability and locale. With no selected scope, use the conservative union. The read-only `--next --capability source_explorer --locale es` command helps inspect readiness; it cannot validate live provider state or authorize an action.

Read the requirement IDs, deliverables, acceptance and verification. Implement one coherent change without expanding into adjacent capabilities. Use installed-version APIs. English identifiers, routes, schema names, reason codes, comments, tests and diagnostics; reviewed Spanish content values. No Livewire questionnaire round trips or ML matching.

Verify acceptance with meaningful tests and required formatting/build checks. Avoid implementation-mirroring tests for trivial reversible edits. Cover an actual failure when fixing a defect. Browser checks in the backlog run through the approved project CI/test environment; they do not authorize operating the user's browser when API-only work is requested.

Append a bounded English journal entry with entryId, workItemId, times, status, commit/tree hash, artifact hashes, commands, outcomes, limitations and blockedBy. Record actual outcomes. Never store secrets, private political vectors or raw user payloads. Update task status/completionEvidence and completionApprovalBindings for required gates, then regenerate/check the plan. Bind completion to the actual retained human packet; a reopened gate may retain historical approvals but still blocks new dependent actions. A local commit is useful when identity is configured; never invent the user's identity or publish a remote automatically.

Select the next eligible item and continue without asking permission for routine reversible steps within the approved blueprint.

## Strict gate procedure

Prepare the entire concrete packet before asking the user. Include gate ID, plan version, action, capability/locale, subject/evidence hash, relevant requirements, actual acceptance results, outstanding risks and rollback/withdrawal procedure where relevant. Include current licence/rights/provider/domain costs before external purchase/provision/publication.

Only an explicit user message approving that packet's scope passes a strict gate. Record authority=human_user, date, exact message/reference, packetHash, subjectHash, action, capability and locale in approvalRecords and approvedScopes. Qualified editorial/privacy/security/fluent review is separate evidence: user authorization cannot manufacture independent review or legal/operational facts.

GATE-01 binds the stable design fingerprint. Status/evidence/journal-only updates leave it stable. Changed definitions, requirements, scope or material assumptions require a new packet. GATE-02–GATE-08 bind actual methodology/release/locale/operator/action subjects; re-check actual state immediately before executing an approved action. The status command conservatively requires this packet verification for actual-state gates.

Gate instances are scoped. Explorer-only acceptance cannot certify questionnaire traffic/storage, regional questions or metrics. A staging provision approval cannot authorize a public release or another domain purchase. An optional metrics or regional gate cannot prevent independently ready Spanish core work.

## When blocked

After at most three focused attempts at the same implementation failure, keep it incomplete, record diagnostics and a concrete recovery proposal, and continue another eligible item. Never weaken a check or mark complete because time elapsed. Human-only inputs and unpublished programmes are external blockers, not implementation failures.

When all eligible work is exhausted, present a consolidated concrete gate/input packet. Do not repeatedly ask the same question or bypass it after waiting. Continue unrelated eligible work. Deferred optional work stays disabled and incomplete; never report the full backlog complete while required work remains.

## Evidence, releases and private matching

Scored stances need exact applicable current-election citations and two actual independent approvals bound to content hashes. Conflicts/pending/ambiguity remain unknown; every candidacy stays visible. No old programme or inferred coalition stance as current evidence. Equal common evidence and original weights precede ordering; insufficient coverage permits cited overlaps/comparisons only.

Input stays in browser memory: no request, URL/hash, cookie, default persistence, telemetry, log, support/crash payload or Boost disclosure. Local downloads require explicit action and clear file-content explanation. Public evidence fetches cannot vary by political selection.

A candidate is a coherent immutable code/data/catalog/algorithm release with compatible schema and verified hashes. Pin sessions, activate atomically and retain correction/withdrawal history. Measure actual privacy/security/accessibility, load and restore on intended assets/infrastructure. Planning checks, a synthetic reference and a scaffold cannot prove production privacy, neutrality or readiness.

## Completion report

List delivered capabilities/locales, actual requirement evidence, approved packets, remaining/deferred items and named operational owners. Report only verified facts. No public launch without applicable human authorization, rights/licences, funding, current runtime/security checks and restore/rollback proof.
